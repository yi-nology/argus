审查 管线

一次审查的旅程：事件 → 多专家 → 确定性裁决 → 双层回帖。

  PR opened / push ─┬─ webhook（签名校验、delivery 幂等）
                    ├─ poller（NAT/VPN 兜底）
                    ├─ POST /tasks（Bearer）
                    └─ MCP review_pr
                            │
                            ▼
              R1 需求解析（改写验收清单 AC-1..N）
              R2 变更理解（diff / 影响面）
              R3 完成度判定（ReAct+工具，证据 file:line）
              R4 多专家并发（builtin / cli / acpx / remote）
              R5 真值表裁决  APPROVE / COMMENT / REQUEST_CHANGES
                            │
                            ▼
              行内评论 + 总结报告（原地更新，不刷屏）

裁决真值表 （零 LLM）

序条件结论
R5.1missing + partial > 0REQUEST_CHANGES（需求未完成，一票否决）
R5.2存在 high findingREQUEST_CHANGES
R5.3unverifiable / 需求模糊 / scope creepCOMMENT（人工确认）
R5.4存在 medium/low findingCOMMENT
R5.5其余APPROVE
R5.3 是防注入兜底：攻击者即使通过注入踢掉难满足的 AC，结果也只是「人工确认」——永远拿不到白给的 APPROVE。

多专家编队

互盲独立（缺省）

成员并发盲审，分歧由 Merger 事后标注「另一专家未复现」——保留分歧信号。

黑板共识（mode: consensus）

成员按轮互看共享黑板，只补他人未覆盖的新问题，一整轮无人补充即收敛——适合高危变更。
