## 阶段 2 · Verified Fix Loop（v7.0 核心）

- **修复分支 + PR 形态**（`ARGUS_FIX_PUSH=1` 缺省新形态）：验证通过的修复推 `argus/fix/<taskID>` 修复分支 + CreateCR 开 PR 进入原审查分支——**不直推任何既有分支**，`argus/fix/` 前缀与保护分支无交集（失败不碰保护分支验收线）。旧直推形态保留为 `ARGUS_FIX_PUSH=direct`（显式选择才启用）。
- **可审计/可回滚/权限可控**：审计 `fix.push`（带 mode）+ 新增 `fix.cr`（created/failed/notified/notify_failed）；回滚 = 关 PR 删分支（`RemoveSourceBranch` 合并即清理）；开 PR 失败降级留痕（分支保留可手动补开），绝不阻塞主链路。
- **防循环护栏**：被审 PR 源分支属 `argus/fix/*` 命名空间 = 本环自产修复 PR → push 环跳过（否则无限开修复 PR）；验证标注照常渲染。
- **Review 环入口**：修复 PR 创建成功后原 PR 回帖带链接（`notifyFixPR`，best-effort 失败只留痕）。
- **能力面**：`get_capabilities` 增 `fix_push_mode`（branch/direct/""）。

## 阶段 3 · 生产运营首切

- **修复闭环运营指标**：`argus_fix_verify_total{result}`（有效率分母）+ `argus_fix_push_total{mode,result}`（分子 pushed/cr_created + 六种失败分因）——直接回答评估验收问题「自动修复有效率是多少」。
- **质量控制台**（#27，两批互补）：`GET /console` 服务端自包含 HTML 页（🔒 read 档，行过滤在 stats/usage 内）——审查概览/Token 消费三口径/失败原因归类（Registry 白名单计数）/修复闭环有效率/按仓明细，数据全来自既有聚合面**零新表**；`cmd/qconsole` CLI（PR #34——HTTPSource 只读拉取 + HTML/文本双形态 + eval 基线趋势，离线可开）。

## 部署注意

- **Schema 变更**：本批无新表（#29 verify 模式复用既有表清单单源 `autoMigrateModels`）。
